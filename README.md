# MidRunJoin · 杀戮尖塔 2 联机中途加入

目标是让朋友在一场已经开始的联机冒险中加入。队伍在两个房间之间暂停，新人选角色、领补给，之后所有人从同一进度继续。真人正式入队前，原队伍始终按原人数游玩，邀请、预览与取消都应保留原有随机状态和遗物池。

**当前进度**　这是一个可编译的 C# mod 骨架。游戏加载入口只输出一条日志。已实测原版三个本地 ENet 进程能进入新建大厅。首次开发里程碑是让两人先开局，到房间边界后加入第三人，完成下一战，再以三人存档退出并重载。邀请、补给、扩员和失败恢复均待实现。

## 构建与加载

在本目录使用 PowerShell 7、.NET 9 SDK 和 Windows 版游戏的本地程序集。项目默认采用本工作区的 Steam 安装路径。

```powershell
dotnet build .\MidRunJoin.csproj -c Release
```

自定义安装目录时，给同一条命令加上 `"-p:GameDir=D:\SteamLibrary\steamapps\common\Slay the Spire 2"`。Release 构建将 DLL 和 JSON 清单一起放进 `dist/MidRunJoin/`。手动测试时，把该文件夹复制到游戏的 `mods/`，使用测试资料启用 mod 并启动游戏。加载成功的日志标记为 `[MidRunJoin] Project skeleton loaded.`。

| 文件 | 职责 |
|---|---|
| [src/Entry.cs](src/Entry.cs) | 游戏通过 `ModInitializer` 调用的入口 |
| [MidRunJoin.csproj](MidRunJoin.csproj) | 引用本机 `sts2.dll`，编译并整理 Release 产物 |
| [MidRunJoin.json](MidRunJoin.json) | mod ID、版本及加载声明。按将来的联机玩法声明为 gameplay mod |
| [原版 ENet 验证脚本](../tools/Test-LocalEnet.ps1) | 工作区共享工具，使用独立测试目录启动三个原版实例 |

## 空席与正式成员

空席数等于原版房间人数上限减去本局正式角色数。断线或托管的成员仍占席位。邀请界面只读这个数，游戏状态里只保存已入队的角色。空席本身无需创建 Player、网络身份、历史条目、随机流或遗物袋。已有两人存档也可以作为原型的起点。

1. 房主收到申请，队伍同意后排队，在旧房间结算完、下一房间尚未生成时保留原检查点。等待界面区分选角色、选奖励和同步阶段。
2. 在独立候选副本中准备新人，保留旧席位顺序，并把新人追加到末尾。只给加入边界建立所需的楼层记录，更早的房间属于当时在场的人。
3. 各端确认预期成员及候选状态后，房主提交一次扩员结果并恢复游戏。准备期间取消、超时或断线，原队伍应能继续；重试沿用该玩家本次补给。已提交身份再次连接走重连流程。
4. 从提交后的下一房间起应用新人数。候选期间的动作、宝箱票位、奖励、队伍效果和就绪判断都以原队伍为准。

## 新人补给草案

房主在检查点冻结统计。设 N 为已有正式角色数，包含断线或托管成员，观战者与候选人不计入。人数至少为一。

| 项目 | 候选规则 |
|---|---|
| 金币 | 最终金币为已有角色金币平均值向下取整 |
| 非先古遗物 | 目标总数为已有角色非先古遗物数的平均值向下取整。保留合法初始遗物，只补差额，差额为负时补 0 件。例如目标为 6、已有 1 件，补 5 件 |
| 卡牌 | 保留初始牌组，奖励次数为各角色牌组张数之和除以 3N 后向下取整。平均 24 张对应 8 次选牌。升级、删牌和附魔尚未纳入公式 |
| 先古遗物 | “层数 ×2”的口径待定。原案暂按每个已到达的先古阶段补两件；平衡备选是按应经历的先古奖励次数补发。两种方案均需适配获得效果、代价与替换流程 |
| 生命、药水 | 暂拟按队伍平均剩余生命比例赋值，药水暂不补。平衡参数留待试玩 |

只从职业、解锁与进度允许的候选中发放遗物。涉及前置条件或二次选择的奖励逐项适配。候选随机流可独立复现，临时遗物袋也必须独立；原版的个人抽遗物接口还会写共享袋。需扣除共享池条目的补给，先记录差额，成功提交时再按原版规则应用一次。取消后，原两人下一只宝箱的候选与袋内顺序都应能逐项对上。

## 实现顺序与验收

| 顺序 | 工作 | 通过条件 |
|---|---|---|
| 1 | ENet 两人检查点，固定新人和固定补给，通过读档大厅扩员 | 三端进入同一节点，新人能出牌、结束回合并领取奖励；原队员不会重领上一房间的奖励 |
| 2 | 保存、二次读档和失败恢复 | 三人身份、席位、牌组、金币、遗物正确；分别在准备、选牌、同步期间掉线，两人检查点都可继续 |
| 3 | 接入完整补给和等待界面 | 重试不能刷补给，获得效果与代价只执行一次；新成员能参与地图投票和共享宝箱 |
| 4 | 空席无副作用和平台验证 | 按下文对照检查取消前后随机流、遗物袋与地图进度；在 Steam 上另验邀请、真实身份和大厅容量 |

第一步可独立开展。未来与托管或观战组合时，托管沿用原角色身份，观战连接始终独立于正式席位。提交确认与崩溃恢复协议仍是原型的设计任务。

## 可行性依据与复现实验

以下证据来自 2026-11-21 的版本复核。程序集检查、离线往返和原版大厅实测各自验证不同环节。

本机 Steam 分支为 `public-beta`，游戏 `v0.113.1`，commit `d09d48e5`，Steam build `26660232`。本次用 ILSpy 检查安装目录中的 `sts2.dll`，SHA-256 为 `62ECBE91093E1FA862DE4329AAC865209DCB297804CAF0F0520D92D8C0B4A9C3`。此结论针对该 beta 构建。官方另有 v0.111.1 主线更新，本次未对主线 DLL 做相同验证。[v0.113.1 官方公告](https://store.steampowered.com/news/app/2868840/view/708914425087656682) · [v0.111.1 官方公告](https://store.steampowered.com/news/app/2868840/view/708914425087656392)

### 当前版本如何接纳第三人

| 环节 | 从本机 DLL 确认的行为 | 对中途加入的影响 |
|---|---|---|
| 连接正在进行的冒险 | `SteamHost` 检查连接者是否在 Steam 大厅中。`RunLobby.OnConnectedToClientAsHost` 和重连请求处理器又检查其是否属于本局 | 单发邀请无法产生新角色。候选人的身份和角色选择应在正式续局连接前确定 |
| 进入读档大厅 | `LoadRunLobby` 在连接和读档加入请求两处按存档玩家的 `NetId` 查找。通过后，房主在 `ClientLoadJoinResponseMessage` 中发送自己的 `SerializableRun` | 可以在房主构造读档大厅之前，将获准新人的真实 ID 和完整角色数据追加到候选存档。已有席位保持原顺序 |
| 重建多人冒险 | `NMultiplayerLoadGameScreen.StartRun` 取出本地身份对应角色，依次调用 `RunState.FromSerializable`、`SetUpSavedMultiplayer` 和 `NGame.LoadRun`，最后一步传入保存的 `PreFinishedRoom` | 新队伍有机会沿正常加载流程初始化。旧 `RunManager.State` 必须先结束，否则 `SetUpSavedMultiplayer` 会抛异常。首个实验可以显式返回读档大厅 |
| 重建同步状态 | `ActionQueueSet` 在构造时按成员建立各自的动作队列。`PlayerChoiceSynchronizer` 可按席位延展选择序号，地图票位则在地点变化时建立 | 只调用 `AddPlayerDebug` 会留下旧动作队列。读档能以三人名单重新构建这些对象 |
| 等待人员到齐 | 普通读档界面的 `ShouldAllowRunToBegin` 在人数不足时允许房主确认继续 | 加入事务须另行确认预期成员的身份和就绪状态。新人选牌或同步中掉线时，应回到两人检查点 |

### 可复现的失败点

游戏进入地图节点时，`RunManager.UpdatePlayerStatsInMapPointHistory` 会遍历当前队伍，对当前历史条目调用 `GetEntry(player.NetId)`。只在存档玩家列表末尾添加第三人，可能让队伍和当前房间历史采用不同的成员名单。

离线实验直接加载该版本 DLL，在内存中创建只含 ID 1、2 的 `MapPointHistoryEntry`。查询 ID 3 抛出异常，内容为 `Player with ID 3 not found in player stats for this run history! We have 1,2`。向当前条目加入 ID 3 后再次查询成功。这证明了具体的失败条件。候选存档应记录加入边界，并为恢复流程会访问的当前条目准备新人记录。更早的房间保留当时的真实成员，另行验证历史界面和结算能处理新人缺席的楼层。

另一个离线探针尝试构造动作队列时，游戏日志组件调用了未初始化的 Godot 原生接口，探针进程退出。动作队列结论来自构造函数检查，其运行验证应在游戏内完成。

### 首个原型怎样选择房间边界

建议把第一次实验放在**队伍已选定下一个普通怪物节点，旧房间已结算，新房间尚未生成**的时刻。`EnterMapPointInternal` 在允许保存时先完成旧房间退出及同步，再调用 `SaveRun(null)`，之后才生成新房间、追加新节点历史。这给出了比“打开地图就暂停”更具体的候选位置。使用此处的原生检查点，并保留地图、已访问坐标、随机状态及房间恢复字段。需要实测重载只进入一次选定节点，且上一房间的奖励保持原值。

1. 房主保留该两人检查点，在副本中生成固定职业的第三人，用真实候选 ID、合法初始牌组、角色随机状态和初始遗物构造完整的可序列化玩家。首次实验固定补给，便于识别重复发放。
2. 通过扩员副本建立有三个席位容量的普通读档大厅，原两人和新人按正式身份加入。候选身份的预先交换、邀请和大厅切换均属 mod 要实现的流程。游戏中的“等待新人选牌”可以在这条路径跑通后封装。
3. 三端进入同一节点，核对地图、旧角色金币与牌组、新人补给。由新人出牌并结束回合，再完成奖励、地图投票与一次共用宝箱分配。
4. 保存、退出，再以三人读档。核对各角色的 `NetId`、席位、卡牌和遗物。再做一次新人准备时掉线的对照，确认两人检查点能继续且未发放补给。

读档会增加重载计数，原版会跳过开局遗物的统一结算，因为获得遗物的效果可能只能执行一次。正式设计需要在候选角色构建时处理新人的遗物收益与代价，并在重试时沿用同一结果。完成三人往返后，再接入上文的新人补给公式。

### 随机状态与遗物

| 需要保留的状态 | 当前实现及扩员约束 |
|---|---|
| 老玩家的个人随机流 | 开局的 `Player.InitializeSeed` 使用冒险种子的确定性哈希加席位索引。续局的 `Player.FromSerializable` 恢复各人已有的随机流、概率和遗物袋。保持两人原有顺序，将新人追加到末尾，只初始化新人。 |
| 共享遗物袋与个人遗物袋 | `RelicGrabBag` 按稀有度保存剩余遗物的顺序。个人奖励路径抽到遗物时也会从共享袋删除该物。补给若调用会修改共享袋的奖励接口，即使用独立随机数，也会改变老玩家未来可见的遗物。应在候选副本明确记录补给消耗哪个袋。 |
| 多人宝箱 | `BeginRelicPicking` 遍历全体玩家，为每个符合条件者掷稀有度，通常再从共享袋抽一件。第三人正式入队后，下一个宝箱可能多抽一次，随后宝箱序列也会分岔。此前的宝箱不能重新生成。 |
| 宝箱见过但没拿到的遗物 | 宝箱分配时，其他玩家自己的袋会尝试把这件遗物移到多人后备队列。常规候选耗尽时可能再次从后备队列取物。所以“曾经看见”不能当成全队永久排除。当前版本的 `RelicGrabBag.ToSerializable` 写入各稀有度主队列，没有写入这个后备队列，也没有写入运行时的刷新配置。需要用同一检查点的普通两人重载作对照，才能区分原版读档差异与扩员额外造成的差异。 |

用实际 DLL 做了一次内存往返实验。问号随机流、共享宝箱随机流和一条个人奖励随机流分别预抽 9 次，通过原版序列化接口恢复，然后逐一对比后续 32 个整数，三条流全部相同。另将问号遇怪概率设为 0.4，往返后仍为 0.4。实验覆盖随机状态恢复，未生成真实宝箱或测量重复遗物的频率。

### 地图、弱怪与问号

- 普通模式的当前幕有 `SavedMap` 时，`GenerateMap` 从已保存的地图构造节点和连线，随后仍会执行地图钩子。应核对当前幕节点类型、连线和已访问坐标。缺少地图数据或含修改地图的 mod 时，不能仅凭相同种子推断结果。
- `ActModel` 预先生成遭遇序列，`RoomSet` 保存遭遇 ID 列表及普通、精英等遭遇各自的访问计数。普通模式中 Overgrowth、Underdocks 的弱遭遇前缀是 3，Hive、Glory 是 2，Blitz 生成时取 1。按普通遭遇计数，不能以走过几层倒推。
- 常规问号掷点中怪物基础概率为 10%。在允许出怪且无其他效果时，每次没出怪加 10 个百分点，出怪后重置。连续三次没出怪，第四次是 40%。首局教学有单独分支，房间黑名单及钩子也会影响结果。续局要保留四类房间当前概率、问号随机流和地图历史。

### 原型对照

1. 在相同版本、种子、角色、解锁、席位顺序和输入下，对比普通双人局与启用空席的双人局。后者反复打开邀请面板、邀请和撤销，经过首次战斗、问号和共享宝箱。逐步比较 RNG 状态、共享和个人遗物袋的顺序（含运行时后备队列）、宝箱候选、遭遇计数、地图及投票人数。
2. 在同一两人检查点准备新人补给后取消。比较准备前后原队伍的上述状态，再执行相同的下一步。若取消流程需要读档，额外与未启用扩员的普通两人重载对照，单独辨认上文记录的原版后备队列差异。
3. 从该检查点真正提交第三人，验证新增身份、补给和楼层记录只出现一次。三人打开下一只宝箱时，记录开始按三人规则抽取的时刻。

上述“零影响”是加入前的玩法与确定性验收要求。当前研究已核对相关原版代码，空席功能尚未实现，以上对照尚未实测。

## 本地 ENet 测试

2026-11-21 在 Windows 上直接运行本机 v0.113.1 public-beta 的三个游戏进程。房主使用 `--fastmp=host_standard --clientId=1`，两个客户端分别使用 `--fastmp=join --clientId=2` 和 `--fastmp=join --clientId=3`。三个进程均使用 `--force-steam=off --nomods --headless`。客户端连接 127.0.0.1 的 UDP 33771 端口；原版房主绑定 0.0.0.0，测试无需配置端口转发。每个进程有独立的 APPDATA、LOCALAPPDATA、临时目录和日志。

房主确认收到两个不同身份的大厅加入请求。客户端 2 收到玩家数为 2 的大厅响应，客户端 3 随后收到玩家数为 3 的大厅响应。脚本结束后关闭了三个测试进程。无窗口模式记录了资源加载相关的警告和 Invalid Task ID，未阻止本次大厅握手。沙箱内启动曾在 .NET 模块初始化时报 Assemblies not found，本次有效数据来自沙箱外的本地运行。

在项目目录用 PowerShell 7 执行 `pwsh -File ..\tools\Test-LocalEnet.ps1` 可重复原版大厅测试。脚本等待房主 PID 监听端口，再逐一启动客户端并核对两端日志。每次运行的测试资料保存在独立目录。[测试脚本](../tools/Test-LocalEnet.ps1)

这套环境可用于同机观察房主与两个独立客户端的同步行为。此次验证止于新建大厅。后续中途加入实验要先让两人开局并推进至检查点，再启动第三人，分别验证运行中申请、扩员副本加载、行动与再次读档。Steam 邀请及 Steam 身份验证需另行覆盖。
